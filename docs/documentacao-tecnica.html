Seção 7.10 · Documentação técnica

Do hardware ao software

Documentação técnica do ColdChainTracker, sistema B2B de rastreabilidade de cadeia fria: sensor ESP32 + DS18B20, ingestão via MQTT, backend Spring Boot com persistência híbrida (PostgreSQL + InfluxDB), telemetria em tempo real via SSE e painel Angular.

1 Arquitetura

Arquitetura de ponta a ponta, organizada em cinco camadas desacopladas.

O ColdChainTracker conecta o sensor físico ao painel web em cinco camadas:

  1. Hardware — ESP32 DevKitV1 + sensor DS18B20 (protocolo OneWire), lendo a temperatura no compartimento de carga e publicando via WiFi.
  2. Mensageria — broker MQTT (Eclipse Mosquitto), desacoplando o sensor do backend.
  3. Backend — Spring Boot: ingestão assíncrona de telemetria, regras de negócio (RN-05, RN-08…), persistência híbrida (PostgreSQL para dados de negócio, InfluxDB para séries temporais), exposição via REST + SSE, geração de certificado em PDF.
  4. Contrato de API — OpenAPI (/v3/api-docs), fonte única de verdade dos tipos, usada para gerar automaticamente o cliente do frontend.
  5. Frontend — Angular SPA (standalone components + signals), consumindo REST para dados históricos e SSE para telemetria ao vivo.

O diagrama de fluxo de dados completo está na seção 7.10.4 Diagramas.

3 Protótipos

Do firmware funcional ao painel web integrado à API real.

Firmware (hardware real)

Sketch ESP32_Arduino.ino funcional — conecta ao WiFi, sincroniza hora via SNTP, lê o DS18B20 a cada 2 segundos e publica no broker MQTT. LED onboard (GPIO2) pisca a cada leitura como indicador visual de atividade.

Simulador de sensor (sem hardware)

Script Python que replica exatamente o contrato de payload do firmware real, permitindo testar o pipeline completo (MQTT → backend → frontend) sem depender de hardware físico. As leituras se movem gradativamente (um pequeno passo por vez, não um valor aleatório independente a cada tick), e o cenário é escolhido via --scenario: compliant permanece dentro da faixa segura o trajeto inteiro (relatório aprovado), non-compliant sobe gradualmente até romper o limite, sustenta a excursão e depois recupera (relatório reprovado) — usado pra validar a geração e normalização de alertas.

Mockups de telas (aprovados)

16 mockups estáticos HTML/CSS cobrindo Login, Registro, Dashboard, Viagens (lista/detalhe), Frota/Veículo/Motorista, Lotes, Alertas (lista/detalhe), Relatórios (lista/detalhe) e Administração (Empresas/Usuários/Limites) — usados como fonte da verdade de layout, espaçamento e cores para a implementação.

5 Fluxo

Do sensor ao certificado de conformidade, ponta a ponta.

  1. O sensor DS18B20 mede a temperatura no compartimento de carga do veículo.
  2. O ESP32 lê o valor a cada 2 s, sincroniza o timestamp via SNTP e publica em coldchain/telemetry/<device_id> no broker Mosquitto: 
    { "device_id": "esp32-001", "temperature": 2.3, "timestamp": "2026-01-01T12:00:00Z" }
  3. O sensor não sabe qual viagem está em andamento — o trip_id nunca é enviado. O backend resolve a viagem ativa a partir do device_id (associado ao veículo), buscando a viagem em status IN_PROGRESS; se não houver, a leitura é descartada silenciosamente.
  4. O backend grava a leitura no InfluxDB (série temporal) e avalia a regra de conformidade conforme o tipo de carga do lote associado à viagem.
  5. Se a temperatura sair da faixa permitida, um alerta é criado/atualizado (WARNING/CRITICAL); ao normalizar, o alerta passa a NORMALIZED (regra RN-05 controla quem enxerga cada alerta).
  6. A leitura é propagada em tempo real ao frontend via SSE, atualizando o gráfico da tela de Detalhe de Viagem sem polling.
  7. Ao concluir a viagem (COMPLETED), o backend agrega o histórico de leituras e gera um certificado de conformidade em PDF, disponível na tela de Relatórios.

7 Decisões técnicas

Escolhas de arquitetura e a razão por trás de cada uma.

  • Persistência híbrida (PostgreSQL + InfluxDB): dados de negócio em banco relacional; leituras de sensor de alto volume em banco de séries temporais — separação motivada por padrão de acesso e volume muito diferentes.
  • MQTT como camada de ingestão IoT: desacopla o firmware do backend; o sensor publica de forma "fire-and-forget", sem conhecer a API REST nem autenticação.
  • trip_id nunca enviado pelo sensor: o hardware (e o simulador, que replica o mesmo contrato) só sabe seu próprio device_id; a associação com a viagem ativa é responsabilidade exclusiva do backend, evitando acoplamento entre hardware e sistema de viagens.
  • SSE em vez de WebSocket/polling: a telemetria é um fluxo unidirecional (servidor → cliente); SSE é mais simples de operar que WebSocket para esse caso de uso e evita o custo de polling.
  • Autenticação stand-in via X-User-Id: a API ainda não tem login real (senha/JWT). Um interceptor injeta esse header em toda chamada do frontend; papel e tipo de empresa são resolvidos uma vez e cacheados em signal — decisão documentada como transitória.
  • Cliente HTTP do frontend gerado, nunca escrito à mão: elimina divergência de contrato; qualquer mudança de DTO no backend obriga regeneração via ng-openapi-gen.
  • Angular standalone + Signals, sem NgRx: a complexidade da aplicação não justifica um state manager externo.
  • Simulador Python replicando o payload exato do firmware: permite testar o pipeline completo, incluindo excursões térmicas, sem depender de hardware físico disponível.
  • Testcontainers em vez de mocks para infraestrutura: os testes de integração sobem instâncias reais de Postgres, InfluxDB e um broker MQTT (HiveMQ), refletindo o comportamento de produção.

8 Testes realizados

Do firmware em campo aos testes de integração do backend.

  • Testes de integração do backend (JUnit + Testcontainers): pipeline completo MQTT → SSE → InfluxDB → geração de relatório de conformidade, além de Companies, Vehicles, Drivers, Meat Batches, Users e Compliance Thresholds.
  • Regras de negócio validadas em teste: RN-08 (transições de status de viagem, incluindo conflito) e RN-05 (visibilidade de alertas por papel/empresa).
  • Testes manuais via Swagger UI: módulo de Viagens (Trips) ponta a ponta, com captura de request/response reais.
  • Testes de geração de certificado: geração e download do PDF de conformidade para um lote real (LC-2026-000003).
  • Testes unitários do frontend: spec por componente Angular (Login, Registro, Shell, Header, Sidebar, Dashboard, ViagensLista, ViagemDetalhe, Frota, DataTable, Button, ComingSoon).
  • Teste de campo do firmware: validação manual do ESP32 + DS18B20 publicando leituras reais via WiFi/MQTT, incluindo verificação do LED indicador e do log serial de erro para sensor desconectado.
  • Simulação de cenários de temperatura: uso do simulador Python (--scenario compliant / --scenario non-compliant) para validar tanto relatórios aprovados quanto a geração e normalização de alertas em uma excursão térmica sustentada, sem hardware físico.
