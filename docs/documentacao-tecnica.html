Seção 7.10 · Documentação técnica

Do hardware ao software

Documentação técnica do ColdChainTracker, sistema B2B de rastreabilidade de cadeia fria: sensor ESP32 + DS18B20, ingestão via MQTT (telemetria, estado de conexão e backfill), backend Spring Boot com persistência híbrida (PostgreSQL + InfluxDB), telemetria em tempo real via SSE, certificado de conformidade em PDF e painel Angular.

1 Arquitetura

Arquitetura de ponta a ponta, do sensor físico até o painel web, organizada em cinco camadas desacopladas.

  1. Hardware — ESP32 DevKitV1 + sensor de temperatura DS18B20 (protocolo OneWire), lendo a cada 2 segundos e publicando via Wi-Fi (2,4 GHz) no broker MQTT.
  2. Mensageria — broker MQTT (Eclipse Mosquitto), desacoplando o sensor do backend. Usa três tópicos por dispositivo:
    • coldchain/telemetry/{device_id} — leituras ao vivo;
    • coldchain/status/{device_id} — estado de conexão, com Last Will;
    • coldchain/backfill/{device_id} — leituras feitas enquanto o sensor estava offline.
  3. Backend — Spring Boot: ingestão assíncrona da telemetria e do backfill, monitoramento do estado de conexão dos sensores, regras de negócio (RN-05 isolamento entre empresas, RN-08 compatibilidade de cargas), persistência híbrida (PostgreSQL para dados de negócio, InfluxDB para séries temporais de sensor), exposição via REST + SSE, detecção de excursões térmicas e geração de certificado PDF.
  4. Contrato de API — OpenAPI (/v3/api-docs), fonte única de verdade dos tipos, usada para gerar automaticamente o cliente do frontend.
  5. Frontend — Angular SPA (standalone components + signals), consumindo REST para dados históricos e SSE para telemetria ao vivo.

Os diagramas de fluxo de dados, entidades, sequência e modelo lógico estão na seção 7.10.4 Diagramas.

3 Protótipos

Do firmware funcional ao painel web integrado à API real.

Firmware (hardware real)

Sketch ESP32_Arduino.ino funcional — conecta ao Wi-Fi, sincroniza hora via SNTP, lê o DS18B20 a cada 2 segundos e publica no broker MQTT. LED onboard (GPIO2) pisca a cada leitura como indicador visual de atividade.

Simulador de sensor (sem hardware)

Aplicação Python que replica o contrato MQTT do firmware real. Tem dois modos: terminal, com um sensor e cenário compliant ou non-compliant (--scenario); e painel web (--ui), que controla vários sensores ao vivo. No painel, cada sensor permite:

  • Ciclo de conexão: ligar, perder sinal, cortar energia e religar com reenvio das leituras offline (backfill);
  • Eventos de temperatura: abertura de porta, pico crítico, falha de refrigeração e falha longa de 16 min;
  • Testes de robustez: JSON malformado, leitura incompleta, backfill no futuro e duplicado.

Inclui também uma verificação ponta a ponta (e2e.py) contra o broker e o backend reais.

5 Fluxo

Do sensor ao certificado de conformidade, ponta a ponta.

  1. O sensor DS18B20 mede a temperatura no compartimento de carga do veículo.
  2. O ESP32 lê o valor a cada 2 s, sincroniza o timestamp via SNTP e publica em coldchain/telemetry/<device_id> no broker Mosquitto: 
    { "device_id": "esp32-001", "temperature": 2.3, "timestamp": "2026-01-01T12:00:00Z" }
  3. O sensor não sabe qual viagem está em andamento — o trip_id nunca é enviado. O backend resolve a viagem ativa a partir do device_id (associado ao veículo), buscando a viagem em status IN_PROGRESS; se não houver, a leitura é descartada silenciosamente.
  4. O backend grava a leitura no InfluxDB e a transmite em tempo real ao frontend via SSE, atualizando o gráfico da tela de Detalhe de Viagem sem polling.
  5. Se o sensor perde a conexão, o broker publica o Last Will e o sistema marca o dispositivo como OFFLINE. Ao reconectar, o sensor reenvia as leituras feitas offline pelo tópico de backfill; o backend descarta duplicadas e leituras com horário no futuro.
  6. Ao gerar um relatório da viagem, o backend analisa o histórico do período e detecta as excursões térmicas conforme o limite de conformidade do tipo de carga (ComplianceThreshold). Cada excursão vira um alerta classificado como:
    • CRÍTICO quando o desvio passa de 2 °C além da faixa, qualquer que seja a duração, ou quando dura mais que a tolerância de 15 min;
    • ATENÇÃO quando é curta e dentro da tolerância, como uma abertura de porta.
    Só alertas críticos reprovam o relatório. A visibilidade dos alertas segue a RN-05: cada empresa vê apenas os das viagens de que participa.
  7. Com a viagem concluída, um usuário gera o certificado de conformidade, disponível em PDF na tela de Relatórios. Ele contém:
    • as estatísticas do período, incluindo a temperatura cinética média (MKT) e os períodos sem dados;
    • as excursões;
    • os limites aplicados, que ficam congelados no certificado.
    Se leituras atrasadas chegarem depois, o relatório ganha uma nova versão, e as anteriores são mantidas.

7 Decisões técnicas

Escolhas de arquitetura e a razão por trás de cada uma.

  • Persistência híbrida (PostgreSQL + InfluxDB): dados de negócio (viagens, empresas, alertas) em banco relacional; leituras de sensor de alto volume em banco de séries temporais — separação motivada por padrão de acesso e volume muito diferentes.
  • MQTT como camada de ingestão IoT: desacopla o firmware do backend; o sensor publica de forma "fire-and-forget", sem precisar conhecer a API REST nem autenticação.
  • trip_id nunca enviado pelo sensor: o hardware (e o simulador, que replica o mesmo contrato) só sabe seu próprio device_id; a associação com a viagem ativa é responsabilidade exclusiva do backend, evitando acoplamento e erros de sincronização entre hardware e sistema de viagens.
  • SSE em vez de WebSocket/polling: a telemetria é um fluxo unidirecional (servidor → cliente); SSE é mais simples de operar que WebSocket para esse caso de uso e evita o custo de polling.
  • Autenticação stand-in via X-User-Id: a API ainda não tem login real (senha/JWT). Um HttpInterceptor injeta esse header em toda chamada do frontend; papel e tipo de empresa do usuário são resolvidos uma vez e cacheados em signal. Decisão documentada como transitória, a ser substituída quando a autenticação completa ("Security Future/v2") for implementada.
  • Cliente HTTP do frontend gerado, nunca escrito à mão: elimina divergência de contrato entre backend e frontend; qualquer mudança de DTO no backend obriga regeneração do cliente via ng-openapi-gen.
  • Angular standalone + Signals, sem NgRx: a complexidade da aplicação não justifica um state manager externo; HttpClient + Signals cobre as necessidades de estado local/reativo.
  • Simulador Python replicando o contrato do firmware: permite testar e demonstrar o pipeline completo sem depender do hardware físico, inclusive excursões térmicas, perda de sinal, queda de energia e backfill, que seriam difíceis de provocar no sensor real.
  • Testcontainers em vez de mocks para infraestrutura: os testes de integração do backend sobem instâncias reais de Postgres, InfluxDB e um broker MQTT (HiveMQ), garantindo que o comportamento testado reflita a infraestrutura de produção.
  • Alertas derivados do relatório, não da leitura isolada: a classificação depende da duração da excursão, que só é conhecida com o histórico do período. Por isso as excursões são detectadas na geração do relatório.
  • Limites de conformidade no banco (migration), não em constantes no código: mudar um valor não exige alterar o código, e cada relatório guarda os limites que aplicou.
  • Alerta identificado por viagem + início da excursão: cada nova versão do relatório recria as excursões, então as ações corretivas são ligadas a esse par, e não ao id da excursão, para não se perderem.
  • Carregamento de relações com @EntityGraph e consulta em lote: evita o problema de N+1 consultas nas listagens, e um teste automatizado garante que o número de consultas não cresce com o volume de dados.
  • Last Will e keep-alive de 15 s no MQTT: o próprio broker avisa quando um sensor cai sem se desconectar, e o sistema identifica a queda em cerca de 22 s.

8 Testes realizados

Do firmware em campo aos testes automatizados de backend, frontend e simulador.

  • Testes automatizados do backend (JUnit + Testcontainers): 360 testes passando, entre unitários e de integração contra Postgres, InfluxDB e broker MQTT reais. Cobrem:
    • o pipeline MQTT → InfluxDB → SSE → relatório;
    • backfill e estado de conexão;
    • classificação com tolerância;
    • MKT (conferida contra cálculo feito à mão) e períodos sem dados;
    • ações corretivas em alertas e isolamento entre empresas;
    • contagem de consultas das listagens, que não pode crescer com o volume.
  • Regras de negócio validadas em teste: RN-08 (transições de status de viagem, incluindo cenário de conflito) e RN-05 (visibilidade de alertas por papel/empresa).

10 Limitações conhecidas

O que ainda não está pronto, documentado de forma explícita.

  • Autenticação provisória: o usuário é identificado pelo header X-User-Id, sem senha nem token; a autenticação completa está prevista para uma versão futura.
  • O firmware ainda publica só telemetria; o estado de conexão, o Last Will e o backfill estão implementados no backend e no simulador.
  • O ESP32 conecta apenas em redes Wi-Fi de 2,4 GHz, e o IP do broker é configurado no código.
  • O detalhe de lote (/lotes/:id) e a tela de ações corretivas ainda não têm interface.
  • A ingestão ao vivo ainda aceita leituras com horário no futuro; só o backfill as descarta.
